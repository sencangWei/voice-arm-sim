# 三个中文机械臂项目源码调研

调研日期：2026-10-25。目标：中文语音指定物体及目的地，在 MuJoCo 中执行新的抓放组合。此次是资料与源码审查，未部署三个项目、未测试其成功率，也未替换现役服务。

## 结论

优先借鉴 Vector OS Nano 的模块化架构，参考子豪兄的中文视觉指令流程。wheelarm-lab 留作以后移动底盘导航参考。不能把任何一个仓库的宣传直接当作我们已经实现的能力。

“无需训练”通常指不为每个新任务采集示范并微调，系统仍使用训练过的语言/视觉模型，以及预先实现的机器人技能、标定和运动控制。它与整条链路使用 VLA 是两种实现路线；两者都需要实际评测泛化与失败恢复。

## 1. 去家门-浪漫人：Vector OS Nano

- [用户所给视频的可读取页面](https://jingxuan.douyin.com/m/video/7619191345878140580)
- [作者明确链接的开源仓库](https://github.com/VectorRobotics/vector-os-nano)
- 本次代码快照：`cd7029aad15d6510c956f504e57181cbb6651996`。

视频正文说明：Claude Haiku 拆任务，Moondream2 识物，EdgeTAM 追踪，Pinocchio 求运动学，ROS2 执行；支持中文及英文。作者同时说明完整 Vector OS 尚未全部开源，Nano 是演示项目。当前仓库已经继续发展，README 默认语言服务写的是 DeepSeek，并有 MuJoCo SO-101 仿真入口，不能混淆视频当时与当前版本。

有用之处：语言规划、视觉感知、机器人技能分层；具有真实图像 VLM 接口、追踪、深度投影、技能注册和验证结构；自带我们偏好的原生 MuJoCo 场景。

必须说明的边界：

1. [`vcli/cli.py` 第 728–742 行](https://github.com/VectorRobotics/vector-os-nano/blob/cd7029aad15d6510c956f504e57181cbb6651996/vector_os_nano/vcli/cli.py#L728) 的默认 SO-101 `--sim` 分支注入 `MuJoCoPerception`。
2. [`mujoco_perception.py`](https://github.com/VectorRobotics/vector-os-nano/blob/cd7029aad15d6510c956f504e57181cbb6651996/vector_os_nano/hardware/sim/mujoco_perception.py) 直接读取场景物体坐标，并用预设中英文别名匹配。这个分支没有从摄像头图像识别物体。使用真值做独立结果评分是合理的，使用真值代替策略视觉输入则不能证明视觉泛化。
3. [`mujoco_gripper.py`](https://github.com/VectorRobotics/vector-os-nano/blob/cd7029aad15d6510c956f504e57181cbb6651996/vector_os_nano/hardware/sim/mujoco_gripper.py) 在夹爪接近物体时启用 weld 约束，把物体固定到夹爪。这适合流程演示，但不能验证靠接触和摩擦完成的可靠抓取。
4. [`perception/pipeline.py`](https://github.com/VectorRobotics/vector-os-nano/blob/cd7029aad15d6510c956f504e57181cbb6651996/vector_os_nano/perception/pipeline.py) 与 [`perception/vlm.py`](https://github.com/VectorRobotics/vector-os-nano/blob/cd7029aad15d6510c956f504e57181cbb6651996/vector_os_nano/perception/vlm.py) 存在图像视觉通路，但还需把 MuJoCo 渲染 RGB-D 接进去，并实际验证。没有证据表明直接启动默认仿真就具备该能力。
5. 本次尚未确认开源版本完整的麦克风语音识别链路，不能把能输入中文等同于已经支持语音。

因此，它是最贴近需求的参考架构，但不能原样启动后就宣称陌生物体识别和真实抓取已经通过。

## 2. 同济子豪兄：vlm_arm

- [仓库](https://github.com/TommyZihao/vlm_arm)
- [README 对应教程视频](https://www.bilibili.com/video/BV1Cn4y1R7V2)
- 本次代码快照：`3534c4b93230a2d5d4398d0f6bd7c43a58c8c8e7`。

对应同名视频“听得懂人话、看得懂图像、指哪打哪的机械臂是怎么炼成的”。源码确实会把中文指令及当前图片交给视觉语言模型，输出搬运对象和目的对象的框，再将像素位置转换到机械臂坐标执行。不是只有预设“酒瓶固定放架子”这一种路线。

主要证据位于 `agent_demo_20250328/utils_agent.py`、`utils_vlm.py`、`utils_vlm_move.py`、`utils_robot.py`。其中使用 MyCobot 与吸泵，二维标定和固定抓放高度；不能直接当作我们平行夹爪、任意三维物体的通用抓取方案。VLM 调用失败后的重试也不等于机械臂抓空后的自主恢复。其输出解析中存在 `eval`，迁移时应改为结构化数据校验。

值得借鉴：中文语义拆解、源物体/目标容器分开定位、在界面展示识别框。需要另外实现三维几何、碰撞检查和结果反馈。

## 3. 任意门：wheelarm-lab

- [仓库](https://github.com/renyimen2026/wheelarm-lab)
- 本次代码快照：`25fdb62fae8ffd340e9e023987a62ff4d0254c45`。

这是 ROS2 Humble、Gazebo、Nav2 的轮臂项目。README 明确说明现阶段语言导航依赖已记录的命名目标点，视觉是单帧 RGB 问答，尚不具备语言驱动抓取。

`wheel_arm_navigation/wheel_arm_navigation/llm.py` 使用本地 Ollama 语言模型，将指令映射为已录入导航位置，提示词还明确拒绝抓取任务；`vision.py` 做图像描述和区域信息，没有形成三维抓取目标或执行控制。

值得借鉴：以后给玩具加移动底盘时的导航和本地模型接入；不能直接解决当前桌面抓放问题。

## 建议我们实际采用的链路

中文语音识别 → 语言模型输出结构化任务（物体、动作、目标容器） → 当前 RGB 图像识别与定位 → 深度及相机标定得到三维位置 → 通用抓取/取出/放置技能 → 新观测验证结果，失败时重新定位或明确报错。

低层抓取技能可以由运动规划和控制程序实现；关键是每次由模型和当前画面决定抓谁、放哪，而不是给每条句子写固定路径。并不强求所有关节动作都由一个大模型直接输出。

沿用 MuJoCo 原生窗口和中文面板。优先验证现有夹爪场景中的视觉任务组合，再考虑改 SO-101；若对照 SO-101，需要单独维护机械臂与相机标定，不能直接挪用原机械臂动作。已有 π0.5 模型可作为对照保留。

## 验收方式

先记录未微调基线，分别测试：酒瓶放碗里、同一酒瓶放架子、香蕉从盘子取出、未为其录过动作的新物体抓放。每类更换位置与措辞，分别统计语义理解、视觉定位、抓取、放置的成功与失败。

策略输入仅允许语言与渲染的摄像头观测；场景真值只进入独立评分器。演示约束吸附与接触物理抓取应分别标注。物体中途移动、抓空时需观察重新定位和恢复过程，不能只演示初始位置固定的一次成功。

这些是下一阶段验收要求，不是本次已通过的结果。新物体仍受基础模型词汇、遮挡、几何可抓取性和机械臂可达范围限制。
